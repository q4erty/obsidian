## 1.3

Неуникальные значения - это те, что встречаются более 1 раза. Поэтому мы можем посчитать количество каждого значения и оставить те, что встречаются более 1 раза.

```sql
SELECT product_id
FROM products
GROUP BY product_id
HAVING COUNT(product_id) > 1;
```

С помощью _**GROUP BY**_ мы сгруппировали все одинаковые **_product_id_** и только после этого оставили только те, количество которых более 1.

`COUNT(product_id)` - в данном случае считает количество каждого одинакового **_product_id_**.

## 1.4

Когда ищем значения по шаблону, то мы можем использовать знак **%**, который заменяет любые символы в условии поиска. Для нашей задачи мы понимаем, что нужные нам клиенты имеют в **_location_** разные написание города и области, но все они начинаются с букв **Моск** _,_ поэтому в условии поиска указываем эти буквы и добавляем знак процента.

```sql
SELECT client_id, location
FROM clients
WHERE location LIKE 'Моск%';
```

## 1.5

Для того чтобы получить все значения из колонки _**location**_ кроме Воронежа и Тулы 0 используем оператор **NOT** **IN** и перечисляем их в скобках. Но не забываем про значения null - чтобы их так же вывести - добавляем второе условие:

```sql
SELECT client_id, location
FROM clients
WHERE location NOT IN ('Воронеж', 'Тула') OR location IS NULL;
```

## 1.6

Для решения этой задача надо четко понимать, когда мы используем **AND** (логическое И) и когда используем **OR** (логическое ИЛИ).

На языке SQL условие задачи будет так: _Получить из таблицы products продукты черного цвета **И** которых меньше 5 штук **ИЛИ** продукты белого цвета **И** которых меньше 10 штук_

SQL запрос, который мы напишем будет выполняться построчно, начиная с первой строки таблицы.

Давайте представим, что первая строка:

|product_id|quantity|color|
|---|---|---|
|131|4|черный|

Строка проверяется на 2 условия - цвет черный **И** количество меньше 5 **ИЛИ** цвет белый **И** количество меньше 10. Первое условия совпало, а значит строка нам вернется в результат.

Вторая строка не удовлетворяет ни одному из двух условию и она соответственно к нам в результат не попадает.

|product_id|quantity|color|
|---|---|---|
|132|12|белый|

И так далее до самой последней строки в таблице.

```sql
SELECT product_id, quantity, color
FROM products
WHERE (color = 'черный' AND quantity < 5) OR (color = 'белый' AND quantity < 10);
```

## Ключевая идея (очень важно)

Количество строк после `JOIN` зависит от двух вещей:

1. **Типа JOIN**
    
2. **Сколько совпадений по `id` и есть ли дубликаты**


Если `id` дублируется → возникает **«взрыв строк»**  
(каждая строка A соединяется с каждой подходящей строкой B)

> **Взрыв строк** — это ситуация, когда из-за **дубликатов ключа** количество строк после `JOIN` **резко увеличивается**.

---

# INNER JOIN

Возвращает **только совпавшие строки**

### Минимум — `0`

**1 вариант**: вообще нет совпадений  
→ нечего соединять  
→ результат пустой

✅ логично

---

### Максимум — `15`

**3 вариант**:

- A: `1,1,1` → 3 строки
    
- B: `1,1,1,1,1` → 5 строк
    

Каждая строка A соединится с **каждой** строкой B:

```
3 × 5 = 15
```

👉 это и есть «взрыв строк»

---

# LEFT JOIN

Возвращает:

- **все строки левой таблицы**
    
- - совпадения из правой
        
- если совпадений нет → `NULL`
    

---

### Минимум — `3`

**1 вариант** (нет совпадений):

```
A.id | B.id
1    | NULL
2    | NULL
3    | NULL
```

👉 все строки A обязаны остаться

---

### Максимум — `15`

**3 вариант** — тот же «взрыв»:

```
3 × 5 = 15
```

---

# RIGHT JOIN

То же самое, но **зеркально**

---

### Минимум — `5`

**1 вариант**:

```
A.id | B.id
NULL | 11
NULL | 12
NULL | 13
NULL | 14
NULL | 15
```

👉 все строки **B** остаются

---

### Максимум — `15`

Опять дубликаты → взрыв строк

---

# FULL JOIN

Возвращает:

- все совпадения
    
- - строки A без пары
        
- - строки B без пары
        

---

### Минимум — `5`

**2 вариант**:

```
A: 3 строки
B: 5 строк
```

Совпали `1,2,3`, а `14,15` — нет.

```
1  1
2  2
3  3
NULL 14
NULL 15
```

👉 минимум всегда **размер большей таблицы**

---

### Максимум — `15`

Если всё дублируется → снова взрыв строк

---

# CROSS JOIN

Без условий ❗

Каждая строка A соединяется **со всеми** строками B:

```
3 × 5 = 15
```

### Поэтому:

- min = 15
    
- max = 15
    

---

## Всё в одной таблице 🧠

| JOIN  | MIN | MAX | Почему                     |
| ----- | --- | --- | -------------------------- |
| INNER | 0   | 15  | нет совпадений / дубликаты |
| LEFT  | 3   | 15  | все строки A сохраняются   |
| RIGHT | 5   | 15  | все строки B сохраняются   |
| FULL  | 5   | 15  | минимум — большая таблица  |
| CROSS | 15  | 15  | декартово произведение     |

---

## Главная мысль, которую стоит запомнить

> **JOIN умножает строки, если ключи не уникальны**

Если хочешь, дальше можем:

- разобрать это на SQL-запросах
    
- показать, как **избежать взрыва строк**
    
- или как **контролировать дубликаты** через `DISTINCT` / `GROUP BY` / подзапросы

```sql
SELECT COUNT(*) FROM A INNER JOIN B ON A.id = B.id

  
SELECT COUNT(*) FROM A LEFT JOIN B ON A.id = B.id

  
SELECT COUNT(*) FROM A RIGHT JOIN B ON A.id = B.id

  
SELECT COUNT(*) FROM A FULL JOIN B ON A.id = B.id

  
SELECT COUNT(*) FROM A CROSS JOIN B
```

## 2.2

Данную задачу можно решить 2 способами - с помощью группировки и оконных функций.  
Рассмотрим оба варианта

_**1 вариант:**_

```sql
WITH department_salary_cte AS(
	SELECT department,
		SUM(salary) AS total_salary
	FROM salary
	GROUP BY department
	)
SELECT s.id_employee, s.department, s.salary, 
	ROUND(s.salary/d.total_salary * 100, 0) AS salary_proc
FROM salary s
LEFT JOIN department_salary_cte d
ON s.department = d.department;
```
С помощью CTE мы создали временную таблицу department_salary_cte, в которой всего 2 колонки - отдел и сумма всех зарплат в этом отделе.

Далее к основной таблице salary присоединили **_department_salary_cte_** по колонке **_department_** и получили для каждой строки соответствующую зарплату всего отдела. 

_**2 вариант (по моему мнению более предпочтителен):**_

```sql
WITH department_salary_cte AS (
	SELECT id_employee, department, salary,
	SUM(salary) OVER (PARTITION BY department) AS total_salary
	FROM salary
	)
SELECT id_employee, department, salary,
	ROUND(salary/total_salary * 100, 0) AS salary_proc
FROM department_salary_cte;
```

С помощью оконной функции `SUM(salary) OVER (PARTITION BY department)` считаем зарплату по отделам и подставляем ее для соответствующего сотрудника в промежуточной таблице _**department_salary_cte**_.  
Здесь важно понимать конструкцию `OVER (PARTITION BY department)` - она делит таблицу на окна из строк с одинаковым отделами и далее для каждой строки подставляет это значение в колонку _**total_salary.**_

## 2.3

```sql
WITH salary_ranked_cte AS(
	SELECT id_employee, department, salary,
		DENSE_RANK() OVER (PARTITION BY department ORDER BY salary DESC) AS rnk
	FROM salary
	)
SELECT id_employee, department, salary
FROM salary_ranked_cte
WHERE rnk = 1;
```

Для рэнжирования зарплат внутри каждого отдела мы применяем оконную функцию `DENSE_RANK()` , которая проставляет ранги по условию, которые описаны после `OVER` :  
`PARTITION BY department` - говорит о том, что ранги проставляться будут только внутри каждого отдела  
`ORDER BY salary DESC` - говорит о том, что максимальная зарплата получит ранг 1, остальные по убыванию будут получать соответствующие ранги.

Далее мы оставляем только те строки где rnk = 1, то есть с максимальными зарплатами внутри каждого отдела.

**Так неправильно,** хотя многие новички допускают такую ошибку:

```sql
SELECT id_employee, department, salary,
	DENSE_RANK() OVER (PARTITION BY department ORDER BY salary DESC) AS rnk
FROM salary
WHERE rnk = 1;
```

Дело в том, что `WHERE` выполняется первее чем `SELECT` и поэтому колонки rnk на этом шаге выполнения запроса не существует.

## 2.5

```sql
SELECT date_id, income,
	SUM(income) OVER (ORDER BY date_id ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS cum_sum
FROM income;
```
или сокращенный вариант (когда у нас нет строк с одинаковыми датами)

```sql
SELECT date_id, income,
	SUM(income) OVER (ORDER BY date_id) AS cum_sum
FROM income;
```

Для подсчета накопительного итога применяем оконную функцию `SUM(income) OVER (ORDER BY date_id)` если колонка для  сортировки  (в данном случае `date_id`) содержит уникальные даты.  
Но если вдруг в ней будет, например две одинаковые даты - то результат для этих дат будет немного отличаться от ожидаемого (смотри закрепленный комментарий).

Лучше использовать первый вариант и важно понимать его суть. Конструкция говорит о том, что перед тем как проставить значение в колонку _**cum_sum**_ СУБД сортирует таблицу по дате от меньшего к большему и для каждой текущей строки суммируется _**income**_ этой строки и всех, что выше.

## 2.6

```sql
SELECT date_id, income,
	ROUND(AVG(income) OVER (ORDER BY date_id ROWS BETWEEN 1 PRECEDING AND 1 FOLLOWING), 0) AS moving_average
FROM income;
```

Используем оконную функцию для расчета скользящего среднего.  
Эта конструкция `OVER (ORDER BY date_id ROWS BETWEEN 1 PRECEDING AND 1 FOLLOWING)` говорит о том, что таблица предварительно сортируется по дате от меньшей к большей, далее для каждой строки в таблице мы определяем так называемой окно, в которое входит текущая строка, 1 строка выше и 1 строка ниже. В этом окне из трех строк считается среднее и проставляется в колонку _**moving_average**_ именно для этой строки.  
Есть ньюанс для первой и последней строки в таблице: у самой первой - нет строки выше, а у самой последней - нет строки ниже. В таких случаях для первой строки скользяшее среднее будет считаться из текущей и следующей даты, а для самой последней из предыдущей и текущей.

## 2.7

_**1 вариант (хороший для понимания оконных функций LAG/LEAD)**_

```sql
WITH cte AS (
	SELECT id,
    action_date,
	LEAD(action_date) OVER (PARTITION BY id ORDER BY action_date) AS next_date
	FROM logs
)
SELECT id, DATEDIFF(next_date, action_date) AS duration
FROM cte
WHERE next_date IS NOT NULL;
```

Используем оконную функцию _**LEAD**_ для получения следующей даты для текущей сессии.

`OVER (PARTITION BY id ORDER BY action_date)` - определяет окна из одинаковых _**id**_ и внутри них сортирует строки по _**action_date**_ от меньшего к большему.  
Предварительный результат (результат в _**cte**_) можно представить таким образом:

|id|status|action_date|next_date|
|---|---|---|---|
|1|start|2024-06-01|2024-06-03|
|1|end|2024-06-03|_null_|
|2|start|2024-06-02|2024-06-18|
|3|end|2024-06-18|_null_|

Важно, что для последних строк внутри каждого окна проставляется null, так как следующий строки в этом окне уже нет.

Далее в основном запросе мы убираем строки где _**next_date**_ null и с помощью функции **_DATEDIFF_** считаем разницу в днях.

_**2 вариант**_

```sql
SELECT id, DATEDIFF(MAX(action_date), MIN(action_date)) AS duration
FROM logs
GROUP BY id;
```

Так как по условию задачи у нас всего 2 возможных статуса, то для каждой сессии длительность будет равняться разнице максимальной и минимальной дат.

3. Теперь для тех продуктов кто входит в тройку фаворитов мы оставляем их оригинальные названия, а для всех остальных - меняем название на "_**другие**_" с помощью оператора _**CASE**_. После этого суммируем количество для того чтобы "_**другие**_" превратились в 1 строку.

```sql
SELECT 
	CASE 
		WHEN rn <= 3 THEN product
		ELSE 'другие'
	END as product,
	SUM(quantity) AS quantity
FROM (
	SELECT product, quantity,
		ROW_NUMBER() OVER (ORDER BY quantity DESC) AS rn
	FROM (
		SELECT product, 
			SUM(quantity) AS quantity
		FROM sales
		GROUP BY product
		) t1
	) t2
GROUP BY 
	CASE
		WHEN rn <= 3 THEN product
		ELSE 'другие'
	END;
```

## 2.10

_**1 Вариант**_

```sql
SELECT d1.date_id,
	COUNT(*) AS rnk
FROM dates d1 JOIN dates d2
ON d1.date_id <= d2.date_id
GROUP BY d1.date_id
ORDER BY rnk;
```
Джойним таблицу саму на себя по условию _**date_id**_ левой таблицы <= _**date_id**_ правой.  
Для максимальной _**date_id = 2025-01-16**_ левой таблицы условию соединения соответствует 1 значение правой (_**2025-01-16**_), поэтому после соединения получится 1 строка с этой датой.  
Теперь возьмем _**date_id = 2025-01-15**_ левой таблицы - для нее условию соединения соответствует уже 2 значения правой таблицы (_**2025-01-16**_ и _**2025-01-15**_), поэтому после соединения получаем 2 строки для этой даты.  
По такому принципу соединяются все оставшиеся строки.  
В итоге для каждой даты левой таблицы считается количество строк, что соответствует нумерации от большего к меньшему.

_**2 вариант**_

```sql
SELECT date_id, (select max(date_id) from dates) - date_id + 1 AS rnk
FROM dates
ORDER BY rnk;
```

Из максимальной даты вычитаем текущую и прибавляем 1.
