Чтобы понять REST (Representational State Transfer), нужно перестать думать о нем как о «протоколе». Это скорее **набор архитектурных ограничений** (правил). Если ты их соблюдаешь — твое API называют **RESTful**.

Вот 6 официальных правил (ограничений) REST, объясненных по-человечески:

---

### 1. Client-Server (Разделение ответственности)

Клиент и сервер должны быть независимы.

- **Суть:** Клиент (фронтенд или твой МС3) не должен знать, как устроена база данных на сервере. Сервер (МС1) не должен знать, как выглядит интерфейс пользователя.
    
- **Зачем:** Ты можешь полностью переписать МС1 на другой язык программирования, и если ты не изменишь URL-адреса, МС3 даже не заметит подвоха.
    

### 2. Stateless (Отсутствие состояния)

Сервер **не должен помнить** ничего о предыдущих запросах клиента.

- **Суть:** Каждый запрос должен содержать **всю информацию**, необходимую для его обработки (токен авторизации, ID пользователя и т.д.).
    
- **Пример:** Сервер не хранит переменную `isLoggedIn = true`. Клиент в каждом запросе присылает «ключ» (Header), подтверждающий его личность.
    
- **Зачем:** Это позволяет легко масштабироваться. Если у тебя 10 серверов, запрос от клиента может попасть на любой из них, и любой сервер его обработает.
    

### 3. Cacheable (Кэширование)

Ответы сервера должны помечаться как «кэшируемые» или «некэшируемые».

- **Суть:** Если клиент запрашивает список городов, который меняется раз в год, сервер говорит: «Запомни это на час». В следующий раз клиент даже не пойдет на сервер, а возьмет данные из своей памяти.
    
- **Зачем:** Это безумно экономит ресурсы сервера и ускоряет работу приложения.
    

### 4. Uniform Interface (Единообразие интерфейса)

Это самое важное и объемное правило. Оно состоит из четырех подпунктов:

1. **Идентификация ресурсов:** Всё есть ресурс, и у него есть уникальный путь (URI). Например: `/users/10`.
    
2. **Манипуляция через представление:** Ты не правишь таблицу в БД напрямую. Ты получаешь JSON (представление), меняешь в нем поле и отправляешь этот JSON обратно.
    
3. **«Самодокументированные» сообщения:** Каждый запрос содержит достаточно инфы, чтобы понять, как его обработать (например, заголовок `Content-Type: application/json`).
    
4. **HATEOAS** (сложная аббревиатура): Сервер в ответе должен присылать ссылки на другие действия. Например, если ты получил данные о заказе, сервер пришлет ссылку на то, как этот заказ оплатить.
    

### 5. Layered System (Многослойность)

Клиент не должен знать, общается он напрямую с сервером или с промежуточным узлом.

- **Суть:** Между твоим МС3 и МС1 может стоять балансировщик нагрузки, прокси-сервер или система безопасности. Для МС3 это выглядит просто как «какой-то сервер».
    
- **Зачем:** Это позволяет добавлять слои защиты и балансировки незаметно для клиента.
    

### 6. Code on Demand (Необязательное)

Сервер может передавать исполняемый код клиенту.

- **Суть:** Например, сервер может отправить JavaScript-скрипт, который клиент должен выполнить. Это единственное необязательное правило REST.
    

---

### Как это выглядит на практике (Хорошо vs Плохо)

|**Ситуация**|**НЕ REST (RPC стиль)**|**RESTful стиль**|
|---|---|---|
|**Получить список**|`GET /getAllMessages`|`GET /messages`|
|**Создать**|`POST /saveNewMessage`|`POST /messages`|
|**Удалить**|`GET /deleteMessage?id=5`|`DELETE /messages/5`|
|**Действие**|Глаголы в URL.|Существительные в URL + Методы HTTP.|

---

### Почему это важно для твоего диплома/проекта?

Если на защите тебя спросят: _"Почему ваше API — это REST?"_, ты должен ответить:

> "Потому что оно **Stateless** (сервер не хранит сессий), использует **стандартные методы HTTP** для управления ресурсами (существительными в URL) и обменивается данными в формате **JSON**."
