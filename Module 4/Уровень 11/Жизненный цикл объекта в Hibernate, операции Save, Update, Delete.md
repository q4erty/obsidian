## 1. Введение: Зачем нужны состояния?

В обычной Java-программе мы используем POJO (Plain Old Java Object) — простые объекты, которые хранят данные и ничего не знают о базах данных.

Однако в Hibernate объект не просто хранит данные. Для того чтобы Hibernate мог отслеживать изменения полей и автоматически генерировать SQL-запросы, у каждого Entity-объекта есть свой **жизненный цикл**. В любой момент времени объект находится в одном из четырех строгих состояний по отношению к `Session` (сессии базы данных).

---

## 2. Четыре состояния объекта в Hibernate

Рассмотрим каждое состояние подробно:

- **Transient (Новый / Переходный / Прозрачный)**.
    
    - **Описание:** Объект только что создан через оператор `new` (например, `new User()`).
        
    - **Связь с БД:** Он еще никак не связан с базой данных, у него нет ID (если генерация автоматическая), и он не привязан к сессии Hibernate. Любые изменения его полей ни на что не влияют.
        
    - _Как перевести дальше:_ Чтобы сохранить его в базу, нужно вызвать методы `session.save()`, `session.persist()` или `session.saveOrUpdate()`.
        
- **Persistent или Managed (Управляемый / Связанный с движком)**.
    
    - **Описание:** Объект жестко привязан к текущей открытой сессии Hibernate.
        
    - **Связь с БД:** Объект имеет реальное отображение (строку) в базе данных.
        
    - _Важное дополнение (Dirty Checking):_ Это самое важное состояние. Если вы измените поле объекта в состоянии _Managed_ (например, вызовете `user.setName("Новое имя")`), вам **не нужно** вызывать метод `update()`. В момент закрытия транзакции (коммита) или вызова `flush()`, Hibernate сам увидит изменения и отправит запрос `UPDATE` в базу.
        
- **Detached (Отсоединенный)**.
    
    - **Описание:** Объект был _Managed_, но сессия, к которой он был привязан, закрылась (или объект был принудительно отсоединен методом `session.evict()`).
        
    - **Связь с БД:** Строка в базе существует, объект в памяти Java существует, но Hibernate больше не следит за изменениями этого объекта.
        
    - _Как перевести дальше:_ Чтобы снова начать отслеживать объект и сохранить изменения, его нужно вернуть в сессию методами `session.update()` или `session.merge()`.
        
- **Removed (Удаленный)**.
    
    - **Описание:** Вы явно сказали Hibernate удалить этот объект (например, вызвали `session.remove()`).
        
    - **Связь с БД:** Объект все еще существует в оперативной памяти Java, но при завершении транзакции строка в базе данных будет удалена с помощью запроса `DELETE`.

## 3. Разные способы получения объекта

Чтобы перевести объект в состояние _Managed_ и начать с ним работать, его нужно достать из базы. В Hibernate/JPA для этого есть несколько методов:

- **`session.get(EntityClass.class, primaryKey)`**. Делает реальный SQL-запрос `SELECT` в базу данных сразу при вызове. Если записи с таким ID нет, метод вернет `null`.
    
- **`session.find(EntityClass.class, primaryKey)`**. Это стандартный метод спецификации JPA (почти полный аналог `get`). Если передать несуществующий ID (например, `-2`), метод также вернет `null`.
    
- **`session.load(EntityClass.class, primaryKey)`**. _Дополнение:_ Это механизм "ленивой загрузки" (Lazy Loading). Метод не делает запрос в БД сразу, а возвращает объект-пустышку (Proxy). Запрос в базу полетит только тогда, когда вы попытаетесь обратиться к любому полю объекта (кроме ID). Если объекта в базе нет, выбросится исключение `ObjectNotFoundException`.

## 4. Удаление объектов (Delete / Remove)

Удаление данных — процесс, требующий осторожности, особенно если таблицы связаны между собой внешними ключами.

### Стандартное удаление через объект

Самый правильный (с точки зрения ООП) способ удалить строку — сначала получить объект из базы, а затем передать его в метод `remove`:

1. `User user = (User) session.find(User.class, user.getId());` — получаем объект из базы.
    
2. `session.remove(user);` — переводим в состояние _Removed_.
    
3. `session.flush();` — принудительно синхронизируем сессию с БД (немедленно отправляем SQL-запрос `DELETE`).
    

### Проблема каскадного удаления (Связанные сущности)

Если вы удаляете пользователя, у которого есть задачи, база данных может выдать ошибку из-за нарушения внешних ключей. Как это решить:

- **На уровне БД:** Добавить ограничение каскадного удаления в SQL (в презентации указано как `CONSTRAINT ONDELETE REMOVE`, но стандартный синтаксис SQL — это `ON DELETE CASCADE`).
    
- **На уровне Hibernate:** Использовать аннотации на связях. Например: `@OneToMany(cascade = CascadeType.ALL, orphanRemoval = true)`. Это скажет Hibernate удалить все дочерние элементы перед удалением родительского.
    

### Массовое удаление (HQL и Native SQL)

Если нужно удалить сразу 1000 записей, вытаскивать каждую через `find()` будет очень долго. Для этого используют прямые запросы:

- **Через HQL:** `session.createQuery("delete from User where id = :id").setParameter("id", user.getId()).executeUpdate();`.
    
- **Через обычный SQL:** `session.createNativeQuery("DELETE FROM user WHERE id = :id").setParameter("id", user.getId()).executeUpdate();`.
    

### Мягкое удаление (Soft Delete)

Часто в бизнесе данные физически не удаляются (чтобы сохранить историю). Вместо этого у записи меняется статус. В таком случае мы достаем объект и просто помечаем его как удаленный: `user.softDeleted();`. Благодаря состоянию _Managed_, Hibernate сам сгенерирует `UPDATE` и сохранит новый статус в базу при закрытии транзакции.
