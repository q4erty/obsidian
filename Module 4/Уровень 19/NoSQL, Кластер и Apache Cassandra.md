## 1. Знакомство с NoSQL базами данных

Базы данных NoSQL отходят от классической реляционной модели, смягчая жесткие требования к непротиворечивости данных (ACID). Они оптимизированы для современных приложений (мобильных, игровых, интернета вещей), работающих с большими объемами информации и требующих низкой задержки.

**Основные преимущества NoSQL:**

- **Гибкость:** Отсутствие строгой схемы (schemaless) позволяет быстро менять структуру данных под нужды приложения, что идеально для неструктурированных данных.
    
- **Горизонтальная масштабируемость:** Базы рассчитаны на масштабирование за счет распределенных кластеров из обычных серверов, а не за счет покупки одного дорогого суперсервера.
    
- **Высокая производительность:** Архитектура затачивается под конкретные шаблоны доступа к данным.
    
- **Широкий функционал:** Наличие специализированных API и типов данных для конкретных задач.

## 2. Типы NoSQL баз данных

NoSQL — это зонтичный термин для нескольких совершенно разных архитектур.

- **Ключ-значение (Key-Value):** Обеспечивают максимальное горизонтальное масштабирование и стабильную задержку в миллисекунды при любых нагрузках. Отличный пример — Amazon DynamoDB (используется для Snapchat Stories).
    
- **Документные:** Данные хранятся в виде иерархических объектов, похожих на JSON. Модель интуитивно понятна разработчикам и идеально подходит для профилей пользователей, каталогов и CMS. Примеры: MongoDB, Amazon DocumentDB.
    
- **Графовые:** Созданы для работы со сложносвязанными данными (социальные сети, графы знаний, рекомендательные системы). Примеры: Neo4j, Giraph, Amazon Neptune.
    
- **БД в оперативной памяти (In-Memory):** Отклик в пределах микросекунд для таблиц лидеров, сессий и real-time аналитики (используется, например, в Tinder). Примеры: Amazon MemoryDB for Redis, ElastiCache.
    
- **Поисковые БД:** Специализированные решения для полнотекстового поиска и потоковой аналитики метрик/логов (например, Amazon OpenSearch, используемый в Expedia).

## 3. Базовые концепции и архитектура NoSQL

Развитие NoSQL обусловлено физическими пределами вертикального масштабирования (частоты процессоров перестали активно расти).

**Ключевые архитектурные решения:**

- **Отсутствие SQL:** Не используется стандартный ANSI SQL DML, хотя некоторые языки запросов пытаются его имитировать.
    
- **Неструктурированность:** Для добавления нового поля в запись не нужно менять структуру всей таблицы.
    
- **Данные в виде агрегатов:** В отличие от реляционных БД, которые дробят сущности по таблицам (нормализация), NoSQL хранит объекты целиком. Это ускоряет чтение в распределенной среде, но усложняет обновление из-за денормализации.
    
- **Shared Nothing (Ничего общего):** Узлы независимы. Главный принцип работы — распределение данных по кластеру.
    
- **Репликация и Шардинг:** Репликация (копирование на другие узлы) повышает доступность. Шардинг (автоматическое разделение данных по узлам) решает проблему пропускной способности.
    
- **Polyglot Persistence:** Мы живем в эпоху «полиглотного хранения» — для разных задач в одном проекте используются разные типы баз данных (симбиоз SQL и NoSQL).

## 4. Apache Cassandra: Введение и Модель Данных

Apache Cassandra — это высокомасштабируемая, распределенная NoSQL база данных, написанная на Java. Она использует гибридную модель: объединяет принцип «ключ-значение» и хранение данных в семействах широких столбцов.

**Иерархия данных в Cassandra:**

- **Пространство ключей (Keyspace):** Аналог схемы БД в реляционной модели, привязано к конкретному приложению.
    
- **Колоночное семейство (Column Family):** Аналог реляционной таблицы, привязано к запросу.
    
- **Запись (Row):** Строка, объединенная ключом (Row key). Ключ определяет, на какой физический узел кластера попадут данные (Partition key).
    
- **Колонка (Column):** Минимальная единица, состоящая из имени, метки времени (timestamp) и значения.
    

В терминах языка Java структуру Cassandra можно описать как `Map<RowKey, SortedMap<ColumnKey, ColumnValue>>`.

## 5. Распределение и Согласованность в Cassandra

Cassandra использует **согласованное хеширование (consistent hashing)**, назначая узлам метки (tokens), что минимизирует пересылку данных при добавлении или падении узла. Размещение ключей чаще всего определяется случайным разметчиком (MD5 хеш ключа), что гарантирует равномерное распределение.

Все узлы в кластере равноценны. Узел, принявший запрос от клиента, становится **координатором**, а узлы, хранящие нужные данные — **узлами-репликами**.

**Уровни согласованности (Consistency Levels):** Разработчик сам выбирает баланс между скоростью и точностью для каждого запроса.

- **ONE / TWO / THREE:** Координатор ждет подтверждения записи/чтения от 1, 2 или 3 узлов соответственно.
    
- **QUORUM:** Координатор ждет ответа от строгого большинства реплик (N/2 + 1). Это золотой стандарт.
    
- **LOCAL_QUORUM / EACH_QUORUM:** Кворум собирается только внутри локального дата-центра (снижает сетевые задержки) или независимо в каждом дата-центре.
    
- **ALL:** Максимальная согласованность, подтверждение от всех реплик.
    
- **ANY (только для записи):** Успех возвращается даже если ни одна реплика недоступна (данные временно оседают на координаторе).

## 6. Механизмы отказоустойчивости

Если что-то идет не так, Cassandra автоматически лечит данные тремя способами:

- **Чтение с восстановлением (Read repair):** При запросе чтения координатор сверяет данные со всех реплик. Данные с самой свежей меткой времени перезаписывают устаревшие данные на отстающих узлах.
    
- **Направленная отправка (Hinted handoff):** Если узел-реплика упал, координатор сохраняет «подсказку» у себя и доставит данные, как только реплика оживет.
    
- **Антиэнтропийное восстановление (Anti-entropy repair):** Ручной фоновый процесс (команда `nodetool repair`), который синхронизирует реплики глобально.

## 7. Внутреннее устройство: Запись, Чтение и Удаление

- **Чтение:** Данные лежат как в памяти, так и в таблицах на диске (SSTables). Для резкого ускорения чтения без лишних обращений к диску используются **Блум-фильтры** (структура, дающая 100% ответ, если ключа нет на диске), **Кэш ключей** (хранит позицию ключа на диске) и **Кэш записей** (хранит всю строку в памяти).
    
- **Уплотнение (Compaction):** Поскольку данные на диск пишутся только последовательно (append-only), со временем накапливается много таблиц. Процесс уплотнения сливает старые таблицы в новые, оставляя только самые свежие значения по меткам времени. Бывает двух видов: уплотнение по размеру (size-tiered) и уплотнение по уровням (leveled).
    
- **Удаление:** Данные не стираются физически сразу. Записывается специальная метка — **tombstone (затирающее значение)**. При чтении система видит tombstone и делает вид, что данных нет. Физическое удаление произойдет позже, во время уплотнения.

## 8. Транзакционность в Cassandra (ACID)

Хотя NoSQL базы обладают слабым ACID, Cassandra гарантирует его выполнение на уровне отдельной записи (строки):

- **Атомарность:** Все колонки одной записи пишутся за одну операцию (или все, или ничего).
    
- **Согласованность:** Достигается настройкой уровней согласованности (например, QUORUM).
    
- **Изолированность:** (С версии 1.1) при чтении записи пользователь увидит либо её полностью старое состояние, либо полностью новое, без перемешивания колонок.
    
- **Долговечность:** Каждое изменение пишется в журнал закрепления (commit log) на диске. В случае краха сервера данные восстанавливаются из него.
