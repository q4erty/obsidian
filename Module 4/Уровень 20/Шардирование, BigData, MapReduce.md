## 1. Что такое шардирование?

Шардирование (Sharding) — это процесс разделения большой таблицы (или коллекции документов/объектов) на более мелкие, управляемые части, называемые шардами. Важно, что объекты не разбиваются на отдельные колонки, а целиком распределяются по разным местам.

Даже если вы разобьете гигантскую таблицу на 16 маленьких внутри одной базы данных на своем локальном ноутбуке, это уже будет считаться шардированием.

**Зачем нужно шардирование?**

- **Увеличение пропускной способности (Bandwidth):** Позволяет обрабатывать объемы данных, которые физически не помещаются на одном сервере, диске или ядре. Нарезав данные, мы можем с ними работать.
    
- **Снижение задержки (Latency):** Сканирование огромной таблицы на одном ядре происходит очень медленно. Шардирование позволяет распараллелить процесс: 20 ядер просканируют 20 небольших таблиц в 20 раз быстрее. При этом время обслуживания отдельных запросов (latency) остается примерно одинаковым для всех воркеров.
    
- **Высокая доступность (High Availability):** Создавая несколько копий (реплик) каждого шарда, мы обеспечиваем отказоустойчивость системы.
    

### Обратная сторона шардирования

Шардирование значительно усложняет логику работы приложения.

- **Усложнение запросов:** Простой запрос `SELECT * FROM documents WHERE id=123` может превратиться в 16 отдельных запросов к разным таблицам.
    
- **Проблема агрегации (Join):** Если нужно выбрать диапазон значений или объединить (join) миллиард записей из одной таблицы с миллиардом из другой, распределенных по сотням шардов, сделать это быстро и эффективно практически невозможно. Придется объединять результаты в коде приложения.
    
- **Закон Амдала:** Идеального распараллеливания не существует. Всегда есть последовательная часть (например, сборка итогового результата для отправки клиенту), которая будет тормозить процесс. Неправильно настроенное шардирование может замедлить работу базы данных на 20-50% за счет увеличения сериализованной части выполнения запроса.
    
- **Решардинг:** Если вы зашардили базу один раз, будьте готовы переделывать это еще несколько раз по мере роста данных.
    

### Как распределять данные (Функция F)

Основной принцип шардирования сводится к формуле: `shard_id = F(object)`. Функция определяет, на какой сервер попадет конкретная запись.

Варианты функций:

- Случайное распределение (`rand() % nums_shards`).
    
- По хешу идентификатора (`somehash(object.id) % num_shards`).
    
- По дате или ID пользователя (`object.date % num_shards`).
    
- По таблице маппинга (`shard_table [ somehash() |… object.date |… ]`).
    

_Совет:_ Выбирайте функцию так, чтобы избежать неравномерного распределения данных (перекосов), когда один шард перегружен, а другие простаивают.

## 2. Big Data и Принципы работы

Большие данные (Big Data) — это подходы и инструменты для обработки структурированных и неструктурированных данных огромных объемов, которые постоянно растут и распределены по множеству узлов сети.

**Ключевые принципы:**

1. **Горизонтальная масштабируемость:** Система должна легко расширяться путем простого добавления новых дешевых серверов в кластер при увеличении объема данных.
    
2. **Отказоустойчивость:** В огромных кластерах (например, у Yahoo более 42 000 машин) поломка оборудования неизбежна. Система должна переживать такие сбои без потери данных и остановки работы.
    
3. **Локальность данных:** Передавать петабайты данных по сети для обработки слишком дорого. Принцип гласит: код (вычисления) должен отправляться туда, где физически хранятся данные.

## 3. MapReduce

MapReduce — это модель распределенной обработки больших данных, придуманная в Google. Она не использует индексы и всегда предполагает полное сканирование данных, поэтому не подходит для запросов, требующих мгновенного ответа.

**Три стадии работы:**

1. **Стадия Map (Отображение):** Пользовательская функция `map()` применяется к каждой входной записи. Она фильтрует и предобрабатывает данные, выдавая на выходе ноль, одну или несколько пар «ключ-значение». Ключ критически важен для следующего этапа. Все функции `map` работают независимо и параллельно на разных машинах (там же, где лежат данные).
    
2. **Стадия Shuffle (Сортировка/Группировка):** Скрытая от пользователя стадия, на которой система сортирует все полученные пары по ключам и раскладывает их по «корзинам». Представляет собой параллельную сортировку.
    
3. **Стадия Reduce (Свертка):** Каждая «корзина» (один ключ + список всех его значений) поступает на вход пользовательской функции `reduce()`. Она вычисляет финальный агрегированный результат для этого ключа. Функции `reduce` также выполняются параллельно.
    

### Стратегии разработки

- **Map Only job:** Если не нужна сортировка и агрегация, можно использовать только стадию Map, что значительно ускорит процесс (так как стадия Shuffle самая тяжелая).
    
- **Combine:** Промежуточная агрегация на стороне `map` перед отправкой данных на `shuffle`. Часто в роли combiner'а выступает сама функция `reduce`, чтобы уменьшить объем передаваемых по сети данных.
    
- **Цепочки задач:** Сложные вычисления разбиваются на последовательности или параллельные ветки MapReduce-задач, управляемые инструментами вроде Oozie или Luigi.
    
- **Distributed Cache:** Механизм, позволяющий разослать нужные файлы (словари, jar-библиотеки, скрипты) на все узлы кластера перед запуском задачи.
    
- **MapJoin:** Если нужно объединить два набора данных (join), и один из них маленький, его можно загрузить в память (через Distributed Cache) и выполнить join прямо на стадии Map, избегая тяжелого ReduceJoin.

## 4. Экосистема Hadoop

Изначально Hadoop был просто реализацией MapReduce и хранилища, но теперь это гигантская экосистема технологий для Big Data.

**Основные компоненты (Core):**

- **HDFS (Hadoop Distributed File System):** Распределенная файловая система для хранения файлов огромного размера.
    
- **YARN:** Фреймворк для управления ресурсами кластера и планирования задач.
    
- **Hadoop Common:** Базовые библиотеки.
    

**Связанные проекты:**

- **Hive:** Транслирует SQL-подобные запросы в задачи MapReduce, делая работу с большими данными доступной для аналитиков.
    
- **Pig:** Высокоуровневый язык скриптов для обработки данных.
    
- **HBase:** Колоночная NoSQL база данных.
    
- **Apache Spark:** Более современный и быстрый (за счет работы в оперативной памяти) движок обработки данных, который постепенно вытесняет классический MapReduce, хоть и использует HDFS/YARN.
    
- **ZooKeeper:** Сервис координации распределенных систем.
    
- **Mahout:** Библиотека машинного обучения для Big Data.

## 5. HBase

HBase — это попытка объединить мощь пакетной обработки Hadoop с возможностью быстрого точечного чтения и обновления данных. Обычные файлы в HDFS для обновлений не подходят.

### Модель данных

- Это распределенная, колоночно-ориентированная, мультиверсионная база "ключ-значение".
    
- Данные хранятся в таблицах, отсортированных по первичному ключу (`RowKey`).
    
- Колонки объединяются в `Column Family` (семейства колонок) на основе паттернов использования. Разные семейства физически хранятся отдельно.
    
- Хранятся несколько версий каждого значения, различающихся меткой времени (`timestamp`).
    
- Удаление происходит не сразу, а ставится метка `tombstone`. Физическая очистка откладывается до операции `Major Compaction`.
    

### Архитектура и Операции

HBase поддерживает простые операции: `Put` (запись), `Get` (чтение по ключу), `Scan` (чтение диапазона записей) и `Delete` (установка tombstone).

Кластер управляется процессом `Master Server`, а сами данные обслуживаются процессами `Region Server`. Каждый сервер работает с `Регионами` (диапазонами ключей), внутри которых есть хранилище (Persistent Storage), память (MemStore) и журнал транзакций (WAL).

### Особенности работы

- Интегрируется с MapReduce из коробки.
    
- Критически важен правильный выбор `RowKey` для равномерного распределения нагрузки. Иначе возникнут «горячие регионы» (перегруженные узлы).
    
- Для массовой загрузки данных используется механизм `BulkLoad` (предварительное формирование HFile через MapReduce), что быстрее обычных `Put` запросов.
    

### Когда использовать HBase?

HBase сложна в администрировании. Её стоит выбирать только если:

1. Данных так много, что они не помещаются на один сервер.
    
2. Данные постоянно обновляются/удаляются (иначе лучше использовать просто файлы в HDFS).
    
3. Нужен как пакетный анализ, так и быстрый точечный доступ по ключу (`RowKey`).
    

Если данные не обновляются, лучше использовать Hive/Impala поверх обычных файлов. Если важна минимальная задержка без пакетной обработки — выбирайте Redis. Если важны транзакции и вторичные индексы — реляционные БД.
