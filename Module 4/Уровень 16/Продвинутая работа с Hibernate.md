## 1. Criteria API

**Criteria API** — это мощный инструмент для написания запросов к базе данных на чистом Java-коде, предоставляющий альтернативу HQL (Hibernate Query Language).

### Основные понятия и структура:

Запрос через Criteria API конструируется с использованием трех основных объектов:

- **CriteriaBuilder:** Фабрика для создания запросов и условий (предикатов). Получается через `session.getCriteriaBuilder()`.
    
- **CriteriaQuery<T>:** Сам объект запроса, где указывается тип возвращаемого результата.
    
- **Root<T>:** Корневой объект, указывающий на сущность (Entity), к которой строится запрос. Аналог секции `FROM` в SQL.
    

### Примеры условий (WHERE):

С помощью `CriteriaBuilder` можно создавать различные условия для фильтрации данных:

- **Больше / Меньше:** `builder.gt(root.get("salary"), 10000)` (зарплата > 10к).
    
- **Like:** `builder.like(root.get("occupation"), "%тест%")`.
    
- **Between:** `builder.between(root.get("salary"), 10000, 50000)`.
    
- **Проверка на null:** `builder.isNull(root.get("name"))` или `builder.isNotNull(...)`.
    

### Продвинутые возможности:

1. **Сложные условия:** Можно комбинировать условия через `builder.or()` и `builder.and()`.
    
2. **Сортировка:** Добавляется через `critQuery.orderBy()`. Направление (ASC/DESC) задается через `builder.asc()` или `builder.desc()`.
    
3. **Агрегация:** Criteria позволяет использовать `count()`, `avg()`, `sum()`, `max()`, `min()`.
    
    - _Пример среднего значения:_ `builder.avg(root.get("salary"))`.
        
4. **Модификация данных:** Существуют классы `CriteriaUpdate` и `CriteriaDelete` для массового обновления или удаления записей без их предварительной загрузки в память.
    

**Когда использовать:** Criteria API незаменим для создания **динамических фильтров** (например, когда на UI много необязательных полей поиска). Если параметр равен `null`, его просто не включают в сборку запроса.

## 2. NativeQuery (Родной SQL)

Если возможностей HQL или Criteria API недостаточно, можно использовать «сырой» SQL.

### Варианты маппинга результатов:

- **Массив объектов (`Object[]`):** Самый простой способ, если нужно выбрать всего пару колонок без привязки к сущности.
    
- **Entity маппинг:**
    
    - _Подход Hibernate:_ `.addEntity(Person.class)`.
        
    - _Подход JPA (более современный):_ `session.createNativeQuery("SQL", Person.class)`.
        
- **DTO маппинг:** Позволяет мапить результат в обычные Java-классы без аннотаций. Это полезно для Read-Only доступа к огромным денормализованным таблицам.
    
- **Несколько классов:** Можно загружать сразу несколько связанных сущностей в одном Native-запросе, используя `addJoin`.
    

**Преимущество:** Максимальный контроль над производительностью. Вы можете выбирать только нужные колонки, игнорировать Lazy Loading и использовать специфические функции конкретной СУБД.

## 3. Транзакции

Транзакция — это группа действий, выполняемых по принципу «все или ничего».

### Виды транзакций в Hibernate:

1. **JDBC-транзакция:** Фактически является транзакцией базы данных, привязанной к конкретному соединению.
    
2. **JTA (Java Transaction API):** Транзакция уровня приложения, которая может охватывать несколько ресурсов (например, две разные БД).
    

### Интерфейс Transaction:

Важно помнить, что создание объекта транзакции и её запуск — это разные вещи (как в классе `Thread`). Транзакцию нужно явно стартовать методом `begin()`.

Основные методы:

- `begin()` — старт;
    
- `commit()` — сохранение изменений;
    
- `rollback()` — откат изменений при ошибке;
    
- `isActive()` / `wasCommitted()` — проверка состояния.
    

Hibernate сам не реализует менеджмент транзакций, он лишь является оболочкой над JDBC или JTA.

## 4. DAO (Data Access Object)

**DAO** — это паттерн проектирования, задача которого — скрыть сложности работы с БД (валидацию, параметры запросов, логику кеширования) за простым интерфейсом.

### Почему это удобно?

- **Изоляция:** Если вы решите перейти с HQL на NativeQuery, код бизнес-логики не изменится.
    
- **Расширяемость:** Легко добавить кеширование или аудит событий внутри DAO-класса.
    
- **Стандартизация:** Большинство DAO имеют набор стандартных методов:
    
    - `getById(id)`, `getAll()`, `getCount()`;
        
    - `save(entity)`, `update(entity)`, `delete(entity)`.
        

Такие повторяющиеся методы рекомендуется выносить в базовый (Generic) класс.

## 5. Полезные нюансы и тестирование

### Работа с несколькими БД

Если приложению нужно работать с двумя базами одновременно (например, читать из одной и писать в другую), проще всего использовать **несколько файлов конфигурации** Hibernate.

### Базы данных в памяти (In-Memory DB)

Для ускорения работы и тестов используются СУБД, работающие целиком в оперативной памяти (например, **H2** или **HSQLDB**). Они легко подключаются как Maven-зависимости.

### Тестирование с Hibernate

Для тестов часто создается «заглушка» на базе In-Memory БД по следующей схеме:

1. `@BeforeAll`: Инициализация соединения с H2.
    
2. `@BeforeEach`: Получение сессии и открытие транзакции.
    
3. `@Test`: Выполнение логики.
    
4. `@AfterEach`: Комитт транзакции.
    
5. `@AfterAll`: Закрытие соединения.
    

**Тестовые данные:** Обычно разделяются на два SQL-файла: `schema.sql` (структура таблиц) и `test-data.sql` (наполнение данными для конкретных тестов).
