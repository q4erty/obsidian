## 1. Проблема наследования (Inheritance Mapping)

В объектно-ориентированном программировании (Java) мы используем наследование (например, `User` -> `Employee`). В реляционных БД данные хранятся в плоских таблицах.

Задача маппинга иерархии — определить, как поля родительского и дочерних классов будут распределены по таблицам.

В JPA/Hibernate существует **4 основные стратегии** маппинга наследования:

1. **MappedSuperclass** (технически не является полноценной стратегией наследования в БД).
    
2. **Single Table** (одна таблица на всю иерархию).
    
3. **Joined Table** (отдельные таблицы для каждого класса со связью по ID).
    
4. **Table Per Class** (отдельные таблицы для каждого класса с дублированием полей).
    

---

## 2. Аннотация `@MappedSuperclass`

Это самый простой способ. Используется, когда у вас есть базовый класс (например, `BaseEntity` с полями `id`, `createdAt`), но вы **не собираетесь** создавать таблицу для этого базового класса или делать по нему полиморфные запросы.

- **Как это работает:** Поля базового класса просто копируются в таблицы всех его наследников.
    
- **Ограничение:** Нельзя выполнить запрос `session.createQuery("from BaseEntity")`.
    
- **Пример:**
    
    Java
    
    ```
    @MappedSuperclass
    public abstract class AbstractTask {
        @Id @GeneratedValue public Long id;
        public String name;
    }
    
    @Entity
    public class Bug extends AbstractTask {
        public String severity; // В таблице Bug будут колонки id, name, severity
    }
    ```

## 3. Стратегия Single Table (Одна таблица на иерархию)

Эта стратегия используется **по умолчанию**, если не указано иное. Все классы иерархии сохраняются в **одну общую таблицу**.

- **Дискриминатор:** Чтобы Hibernate понимал, какой объект какой строке соответствует, добавляется специальная колонка — **Discriminator**. По умолчанию она называется `DTYPE` и хранит имя класса.
    
- **Плюсы:** Высокая производительность (нет JOIN-ов), простые запросы.
    
- **Минусы:** Все колонки дочерних классов в БД должны разрешать `NULL` (потому что в строке "Bug" поля от "Feature" будут пустыми).
    

**Аннотации:**

- `@Inheritance(strategy = InheritanceType.SINGLE_TABLE)` — на родительском классе.
    
- `@DiscriminatorColumn(name = "type")` — настройка имени колонки-маркера.
    
- `@DiscriminatorValue("B")` — на дочернем классе (что именно записать в колонку типа).
    

---

## 4. Стратегия Joined Table (Соединенные таблицы)

Каждый класс в иерархии имеет свою таблицу. Таблица дочернего класса содержит только его уникальные поля и внешний ключ (он же Primary Key), ссылающийся на ID родителя.

- **Плюсы:** Соблюдается нормализация БД, можно ставить ограничения `NOT NULL`.
    
- **Минусы:** Для получения данных о дочернем объекте Hibernate приходится делать `JOIN` с родительской таблицей. Чем глубже иерархия, тем медленнее запросы.
    

**Аннотации:**

- `@Inheritance(strategy = InheritanceType.JOINED)` на родителе.
    

---

## 5. Стратегия Table Per Class (Таблица для каждого класса)

Для каждого конкретного класса создается абсолютно независимая таблица, которая содержит **все** поля (и свои, и унаследованные).

- **Особенность:** В отличие от `MappedSuperclass`, здесь можно делать полиморфные запросы.
    
- **Минусы:** При запросе всех объектов через родительский класс Hibernate будет использовать `UNION`, что может быть очень медленно на больших данных. Дублирование структуры колонок в БД.
    

**Аннотации:**

- `@Inheritance(strategy = InheritanceType.TABLE_PER_CLASS)`
    

---

## 6. Полиморфные запросы (HQL/JPQL)

Одно из главных преимуществ правильного маппинга наследования — возможность работать с объектами разных типов единообразно.

**Примеры из презентации:**

1. **Выбрать всех:** `from Task` (вернет и `Bug`, и `Feature`, если они наследуются от `Task`).
    
2. **Фильтрация по типу:** `from Task where type(t) = Bug` (использование функции `type()`).
    
3. **Использование в условиях:** `select t from Task t where t.employee.name = 'Иван'` — Hibernate сам поймет, в каких таблицах искать, в зависимости от выбранной стратегии.

## Итоговая таблица сравнения:

|**Характеристика**|**Single Table**|**Joined Table**|**Table Per Class**|
|---|---|---|---|
|**Производительность**|Очень высокая|Низкая (из-за JOIN)|Средняя (из-за UNION)|
|**Нормализация БД**|Плохая (много NULL)|Отличная|Средняя|
|**Полиморфные запросы**|Очень быстрые|Сложные JOIN|Сложные UNION|
|**Когда выбирать**|Когда подклассов мало и у них немного своих полей|Когда важна чистота БД и строгие ограничения (NOT NULL)|Используется редко, когда нужно полное разделение данных|

_Дополнение:_ При выборе стратегии всегда начинайте с **Single Table**, так как она наиболее эффективна. Переходите на **Joined**, только если количество `NULL` колонок в базе становится критическим или бизнес-логика требует жестких ограничений на уровне БД.
