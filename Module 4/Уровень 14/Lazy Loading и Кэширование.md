## 1. Отложенная загрузка (Lazy Loading)

### Предыстория проблемы

При работе с базой данных на этапе проектирования крайне важно думать об оптимизации. Изначально Hibernate спроектирован так, чтобы делать работу с БД удобной, позволяя легко получать любые дочерние объекты родительской сущности. Однако, если Hibernate попытается загрузить все связанные данные одним огромным SQL-запросом, это приведет к серьезным проблемам.

В качестве примера представьте ситуацию, когда вам нужно получить данные пользователя, у которого есть несколько тысяч комментариев. Если загрузить их все сразу, они займут слишком много оперативной памяти. Именно поэтому загружать все связанные данные по умолчанию нельзя.

### Стратегии выборки: EAGER и LAZY

Для решения этой проблемы в Hibernate (и JPA) используется параметр `fetch`, который указывается в аннотациях связей (например, `@OneToMany`, `@ManyToMany` и т.д.). Этот параметр принимает два основных значения:

- **`FetchType.EAGER` (Жадная загрузка):** При загрузке родительской сущности будут немедленно загружены и все ее дочерние сущности.
    
- **`FetchType.LAZY` (Ленивая загрузка):** При загрузке родителя дочерняя сущность (или коллекция) загружена не будет. Вместо реальных данных будет создан специальный **proxy-объект** (объект-заместитель). Hibernate будет отслеживать обращения к этому proxy-объекту и загрузит реальные данные из базы данных только в момент первого фактического обращения к ним. **Пример использования LAZY на практике:**
    

Java

```
// 1. Загружаем пользователя. Комментарии еще НЕ загружены из БД (там proxy)
User user = session.load(User.class, 1); [cite: 109]
List<Comment> comments = user.getComments(); [cite: 109]

// 2. В момент начала итерации происходит реальное обращение к данным. 
// Именно здесь Hibernate делает отдельный SQL-запрос за комментариями!
for (Comment comment : comments) { [cite: 109]
    System.out.println(comment); [cite: 110]
} [cite: 111]
```

### 💡 Дополнение: Значения по умолчанию

В презентации упоминается, что если вы не укажете параметр `fetch` в аннотации, Hibernate будет использовать значения по умолчанию. Но какие они?

- Для связей **«Ко Многим»** (`@OneToMany`, `@ManyToMany`) по умолчанию используется **`LAZY`**. Это логично, так как коллекция может быть огромной.
    
- Для связей **«К Одному»** (`@ManyToOne`, `@OneToOne`) по умолчанию используется **`EAGER`**. Загрузить один связанный объект обычно не так "дорого" для памяти.

## 2. Использование JOIN FETCH

_Дополнение: Почему это нужно?_ Хотя `LAZY` решает проблему нехватки памяти, он порождает другую проблему — **N+1 SELECT**. Если вы загрузите список из 100 пользователей, а затем в цикле начнете запрашивать комментарии каждого, Hibernate выполнит 1 запрос на пользователей и еще 100 отдельных запросов на комментарии (всего 101 запрос).

Чтобы избежать этого в случаях, когда мы точно знаем, что дочерние объекты нам понадобятся сразу, разработчики используют конструкцию **`JOIN FETCH`** в HQL запросах. Она заставляет Hibernate проигнорировать настройку `LAZY` и загрузить данные сразу одним запросом.

**Пример из презентации:**

Java

```
// Использование left join fetch для немедленной загрузки сотрудника вместе с задачей
String hql = "select distinct task from Task t left join fetch t.employee order by t.deadline"; [cite: 115]
Query<Task> query = session.createQuery(hql, Task.class); [cite: 116]

// Дополнительно показана пагинация (лимитирование результатов)
query.setFirstResult(0); [cite: 117]
query.setMaxResults(1); [cite: 117]
return query.list(); [cite: 118]
```

## 3. Кэширование данных (Caching)

Кэширование — это сохранение часто запрашиваемых данных в быстрой памяти (ОЗУ), чтобы не делать повторные медленные запросы к базе данных.

_💡 Дополнение: В Hibernate существует два основных уровня кэша:_

1. **Кэш первого уровня (L1):** Включен по умолчанию. Привязан к сессии (`Session`). Живет, пока жива сессия.
    
2. **Кэш второго уровня (L2):** Опциональный. Привязан к фабрике сессий (`SessionFactory`) и разделяется между всеми потоками/сессиями в приложении.
    

### Настройка кэша второго уровня

В презентации демонстрируется включение кэширования на уровне сущности с помощью специальной аннотации:

Java

```
@Cache(usage = CacheConcurrencyStrategy.READ_WRITE) [cite: 126]
```

Эта аннотация указывает Hibernate, что данную сущность нужно кэшировать, и задает стратегию конкурентного доступа (в данном случае `READ_WRITE`, что означает, что данные могут как читаться, так и обновляться).

### Настройка кэша запросов (Query Cache)

Обычный кэш L2 хранит объекты по их ID. Но если вы делаете поиск по другим параметрам (например, "найти всех сотрудников с именем Иван"), Hibernate не знает, какие ID вернутся, поэтому выполняет SQL-запрос. Чтобы закэшировать _результаты самих запросов_, нужен Query Cache.

**Как это настраивается:**

1. Сначала необходимо глобально включить кэш запросов в конфигурационном файле Hibernate (например, `hibernate.cfg.xml`):
    
    XML
    
    ```
    <property name="hibernate.cache.use_query_cache" value="true"/> [cite: 133]
    ```
    
2. Затем для каждого конкретного запроса нужно явно указать, что его результаты следует поместить в кэш:
    
    Java
    
    ```
    // Создаем запрос
    Query query = session.createQuery("from Employee where id = 4"); [cite: 134]
    
    // Явно разрешаем кэширование для этого запроса
    query.setCacheable(true); [cite: 134]
    
    // Получаем результат (при первом вызове он пойдет в БД и сохранится в кэш, 
    // при последующих - вернется из кэша)
    Employee director1 = query.uniqueResult(); [cite: 135]
    // Аналог в одну строку из презентации:
    // Employee director1 = session.createQuery("from Employee where id = 4").uniqueResult(); [cite: 132]
    ```
