## 1. Минусы многопоточности (Race Condition)

Главная проблема — когда несколько нитей одновременно пытаются изменить одни и те же данные.

- **Пример:** Представьте банковский счет.
    
    - Нить А хочет снять 100$. Она проверяет баланс (там 100$), но не успевает списать.
        
    - Нить Б тоже проверяет баланс (там всё еще 100$) и снимает их.
        
    - Нить А "просыпается" и тоже снимает 100$.
        
    - **Итог:** Сняли 200$, хотя было всего 100$.
    

Это происходит из-за того, что операции (чтение, изменение, запись) не являются _атомарными_ (неделимыми). Процессор может переключиться на другую нить посередине операции.

## 2. Ключевое слово `synchronized`

Чтобы решить проблему гонки данных, нужно закрыть доступ к общим данным для всех, кроме одной нити. Этот механизм называется **Мьютекс** (Mutex — Mutual Exclusion).

В Java у каждого объекта есть встроенный мьютекс. Использовать его можно с помощью слова `synchronized`.

### Вариант А: Синхронизированный блок

Мы явно указываем объект, чей мьютекс (замок) хотим захватить.

``` java
Object lock = new Object();

public void doSomething() {
    // Нить ждет здесь, пока lock не освободится
    synchronized (lock) { 
        // Внутри может находиться только одна нить одновременно
        count++; 
    }
}
```

### Вариант Б: Синхронизированный метод

Если написать `synchronized` в объявлении метода, то блокировка ставится на объект `this` (для нестатических методов) или на класс (для статических).

``` java
public synchronized void doSomething() {
    count++;
}
// Это то же самое, что synchronized(this) { ... }
```

## 3. Проблема видимости памяти и `volatile`

Нити могут кэшировать переменные в своей локальной памяти (кэш процессора), чтобы работать быстрее.

- **Проблема:** Одна нить изменила переменную, а вторая нить "не видит" этого изменения, потому что читает старое значение из своего кэша.
    
- **Решение:** Ключевое слово `volatile`.
    
    - Оно говорит компилятору и JVM: "Эту переменную нельзя кэшировать. Всегда читай и пиши её сразу в общую (медленную) память".
        
    - `volatile` гарантирует **видимость**, но **не атомарность** (не спасет от гонки данных при инкременте `i++`).

## 4. Управление потоками: `yield` и `join`

### `Thread.yield()`

- Это подсказка планировщику потоков.
    
- **Смысл:** Текущая нить говорит: "Я готова уступить свое время процессора другим нитям такой же важности".
    
- Это не гарантирует остановку, просто переводит нить из состояния "Running" в "Runnable".


### `thread.join()`

- Используется для ожидания завершения другой нити.
    
- **Пример:** Главная нить (`main`) должна дождаться, пока `thread2` скачает файл, прежде чем продолжить.

``` java
Thread t2 = new Thread(...);
t2.start();
// ... какой-то код ...
t2.join(); // Main остановится здесь и будет ждать, пока t2 не умрет (закончит работу)
System.out.println("Файл скачан!");
```

## 5. Взаимная блокировка (DeadLock)

Это ситуация, когда программа зависает навечно, потому что нити ждут друг друга.

- **Сценарий:**
    
    1. Нить 1 захватила объект А и хочет захватить объект Б.
        
    2. Нить 2 захватила объект Б и хочет захватить объект А.
    
- **Результат:** Никто не может продолжить работу.
    
- **Как избегать:** Следить за порядком захвата ресурсов (всегда захватывать в одном и том же порядке: сначала А, потом Б).

## 6. Условия синхронизации памяти (Happens-Before)

Java гарантирует строгий порядок видимости изменений в памяти в определенных случаях ("Happens-Before" relationship):

1. **Освобождение монитора** (выход из `synchronized`) происходит _до_ того, как другая нить захватит этот же монитор. Все изменения, сделанные первой нитью, станут видны второй.
    
2. **Запись в `volatile`** происходит _до_ чтения этой переменной.
    
3. **Старт потока:** Все, что было сделано до вызова `thread.start()`, будет видно внутри запущенного потока.
    
4. **Завершение потока:** Все, что сделала нить, будет видно тому, кто вызвал `thread.join()` и дождался её конца.
