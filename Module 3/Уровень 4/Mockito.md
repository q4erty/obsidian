## 1. Введение: Зачем нужен Mockito?

Когда мы пишем Unit-тесты (например, с помощью JUnit), мы должны тестировать работу **только одного конкретного класса**.

Но в реальных проектах классы сильно связаны друг с другом. Например, сервис авторизации (`AuthService`) для своей работы обращается к базе данных (`UserRepository`).

- **Проблема:** Если мы будем тестировать `AuthService` с реальным `UserRepository`, это уже будет не Unit-тест, а интеграционный тест. Нам придется поднимать базу данных, следить за ее состоянием, тесты станут медленными и хрупкими.
    
- **Решение:** Использовать **Mock-объекты (моки/заглушки)**. Мы подменяем реальный `UserRepository` на «пустышку», которая притворяется настоящей базой данных, но работает только в памяти и делает строго то, что мы ей скажем.
    

**Mockito** — это самый популярный фреймворк в Java для создания таких заглушек.

---

## 2. Подключение Mockito к проекту

Чтобы начать использовать фреймворк, его нужно добавить как зависимость в `pom.xml`.

XML

```
<dependency>
    <groupId>org.mockito</groupId>
    <artifactId>mockito-core</artifactId>
    <version>4.2.0</version> <scope>test</scope> </dependency>
```

---

## 3. Создание моков

По умолчанию mock-объект ничего не делает. Все его методы, возвращающие объекты, возвращают `null`, возвращающие числа — `0`, а булевы — `false`.

**Способы создания:**

1. **Через метод `mock()`:**
    
    Java
    
    ```
    List<String> mockList = Mockito.mock(List.class);
    ```
    
2. **Через аннотации (современный подход):**
    
    Используется аннотация `@Mock`. _Дополнение: чтобы аннотации заработали в JUnit 5, класс с тестами нужно пометить аннотацией `@ExtendWith(MockitoExtension.class)`._
    

---

## 4. Обучение моков (Stubbing)

Мы можем "научить" нашу заглушку возвращать нужные нам данные при вызове определенных методов. Для этого используется конструкция `when(...).thenReturn(...)`.

**Пример:**

Java

```
// Учим мок: когда кто-то вызовет get(0), верни "Первый элемент"
Mockito.when(mockList.get(0)).thenReturn("Первый элемент");

System.out.println(mockList.get(0)); // Выведет: Первый элемент
System.out.println(mockList.get(99)); // Выведет: null (мы этому не учили)
```

_Также можно заставить мок выбросить исключение (например, для проверки негативного сценария):_

`Mockito.when(mockList.get(1)).thenThrow(new RuntimeException());`

## 5. Проверка поведения (Verification)

Это центральная тема презентации. Иногда метод ничего не возвращает (`void`), но мы хотим убедиться, что он **действительно был вызван** внутри нашего тестируемого кода (например, был вызван метод сохранения в БД `save()`).

Для этого используется метод **`Mockito.verify()`**.

### Базовый синтаксис:

`Mockito.verify(объект, количество).имяМетода(параметр);`

### Настройка количества ожидаемых вызовов:

Вместо параметра `количество` мы можем передавать специальные методы Mockito для точной проверки:

- **`times(n)`**: Метод должен быть вызван ровно `n` раз. _(Если не указать количество, по умолчанию используется `times(1)`)._
    
- **`never()`**: Метод **не** должен быть вызван ни разу (аналог `times(0)`).
    
- **`atLeast(n)`**: Метод должен быть вызван как минимум `n` раз.
    
- **`atLeastOnce()`**: Метод должен быть вызван хотя бы один раз (аналог `atLeast(1)`).
    
- **`atMost(n)`**: Метод должен быть вызван не более `n` раз.
    
- **`only()`**: Должен быть вызван **только** этот метод у данного мок-объекта, и никакие другие методы больше не вызывались.
    

**Пример в коде:**

Java

```
mockList.add("Apple");
mockList.add("Apple");

// Проверяем, что метод add("Apple") был вызван ровно 2 раза
Mockito.verify(mockList, Mockito.times(2)).add("Apple");

// Проверяем, что метод clear() ни разу не вызывался
Mockito.verify(mockList, Mockito.never()).clear();
```

## 6. Проверка порядка вызовов (InOrder)

Иногда важно не просто проверить, что методы были вызваны, но и убедиться, что они были вызваны в **строго определенном порядке**. Для этого используется класс `InOrder`.

**Как это работает:**

1. Создается объект `InOrder`, в который передаются моки, за которыми нужно следить.
    
2. Вызовы `verify` делаются не через `Mockito`, а через созданный объект `InOrder`. Если реальный порядок выполнения нарушен, тест упадет.
    

**Пример:**

Java

```
List<String> mockList = Mockito.mock(List.class);

// Выполняем действия
mockList.add("Первый");
mockList.add("Второй");

// Создаем проверяльщик порядка для объекта mockList
InOrder inOrder = Mockito.inOrder(mockList);

// Проверяем порядок
inOrder.verify(mockList).add("Первый"); // Ожидаем, что это было сначала
inOrder.verify(mockList).add("Второй"); // А это — потом
```

> **Резюме лекции:** Фреймворк Mockito позволяет отрезать ваш код от внешних зависимостей. Вы создаете заглушки (`mock`), описываете, как они должны реагировать на вызовы (`when/thenReturn`), и в конце проверяете, правильно ли ваш код взаимодействовал с этими заглушками (`verify`, `InOrder`).
