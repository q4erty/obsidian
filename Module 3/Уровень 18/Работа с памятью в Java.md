## 1. Организация памяти в JVM (Где хранятся данные?)

Когда вы запускаете Java-приложение, виртуальная машина (JVM) запрашивает у операционной системы кусок оперативной памяти и делит его на несколько логических областей. Две самые важные из них — это **Стек (Stack)** и **Куча (Heap)**.

### А. Стек (Stack Memory)

Стек используется для выполнения потоков (threads). У **каждого потока есть свой собственный стек**, который недоступен другим потокам.

- **Что здесь хранится:** * Вызовы методов (каждый вызов метода создает в стеке новый блок — _фрейм_).
    
    - Локальные переменные примитивных типов (`int`, `double`, `boolean` и т.д.), созданные внутри метода.
        
    - **Ссылки** на объекты (сами объекты здесь не лежат, только «адреса» (указатели) на них).
        
- **Особенности:** Стек работает очень быстро (по принципу LIFO — последним пришел, первым ушел). Память очищается автоматически и моментально, как только метод завершает работу (фрейм удаляется). Если стек переполняется (например, при бесконечной рекурсии), вылетает ошибка `StackOverflowError`.
    

### Б. Куча (Heap Space)

Куча — это общая область памяти для всего приложения. Она **одна на все потоки**.

- **Что здесь хранится:** * Абсолютно **все объекты** (созданные через `new`), включая массивы и строки. Даже если вы создали объект внутри метода, сам объект ляжет в Кучу, а в Стек попадет только ссылка на него.
    
    - Поля классов (переменные экземпляра), так как они являются частью объектов.
        
- **Особенности:** Доступ к куче медленнее, чем к стеку. Память здесь не очищается автоматически при выходе из метода — этим занимается Сборщик мусора (Garbage Collector). Если куча заполняется полностью, программа падает с ошибкой `OutOfMemoryError`.
    

### В. Metaspace (Метапространство)

Раньше эта область называлась _PermGen_. Здесь хранятся метаданные самой программы: код загруженных классов (структура), статические переменные (`static`) и константы.

## 2. Java Memory Model (JMM) — Модель памяти Java

Многопоточность — это сложно. JMM — это набор строгих правил, которые описывают, как потоки должны взаимодействовать с общей памятью (Кучей).

- **Проблема видимости:** Процессоры компьютеров имеют свои быстрые локальные кэши (L1, L2). Когда поток хочет изменить значение общей переменной (например, `count++`), он может скопировать ее из главной памяти (Heap) в свой локальный кэш процессора, изменить там, но **не сразу** записать обратно в главную память. Из-за этого другие потоки могут продолжать видеть старое значение переменной.
    
- **Решение (volatile):** Ключевое слово `volatile`. Если пометить переменную как `volatile`, мы говорим JVM: "Не кэшируй эту переменную! Все чтения и записи должны идти напрямую в главную память". Это гарантирует, что изменение переменной одним потоком моментально станет видно всем остальным потокам.
    
- **Happens-before (Происходит до):** Базовый принцип JMM, гарантирующий порядок выполнения операций. Если действие А _happens-before_ действия Б, то результат действия А будет гарантированно виден потоку, выполняющему действие Б.

## 3. Сборка мусора (Garbage Collection - GC)

В языках вроде C++ программист должен сам очищать память (удалять объекты). В Java за это отвечает фоновый процесс — **Garbage Collector**.

**Как GC понимает, что объект больше не нужен?**

GC ищет так называемые _GC Roots_ (корневые точки — например, активные локальные переменные в стеке, статические переменные). Затем он обходит все ссылки, ведущие от этих корней. Все объекты, до которых он **смог дотянуться**, считаются "живыми". Те объекты, до которых нет ни одной цепочки ссылок (они "висят в воздухе"), признаются мусором и удаляются.

### Гипотеза о поколениях (Generational Hypothesis)

Большинство объектов в Java живут очень недолго (создались в методе, отработали и умерли). Опираясь на это, создатели JVM разделили Кучу (Heap) на два поколения, чтобы не сканировать всю память каждый раз:

1. **Young Generation (Молодое поколение):** Здесь создаются все новые объекты. Это небольшая область, поэтому GC работает здесь часто (Minor GC) и очень быстро. Мусор удаляется, а выжившие объекты перемещаются в следующее поколение.
    
2. **Old / Tenured Generation (Старое поколение):** Сюда попадают объекты-долгожители, которые пережили уже несколько циклов сборки мусора в молодом поколении (например, кэши, коннекты к БД). GC заглядывает сюда редко (Major GC), но процесс очистки старого поколения занимает много времени и может вызывать "паузы" в работе программы (Stop-the-world).

## 4. Типы ссылок в Java (Reference Types)

Обычно, если на объект есть ссылка, сборщик мусора его не трогает. Но в Java (в пакете `java.lang.ref`) существуют специальные виды ссылок, которые позволяют гибко управлять поведением GC.

1. **Strong Reference (Сильная ссылка):** Обычная ссылка (`Object obj = new Object()`). Пока на объект есть хотя бы одна сильная ссылка, GC **никогда** его не удалит. Программа скорее выбросит `OutOfMemoryError`.
    
2. **Soft Reference (Мягкая ссылка):** GC удалит объект по такой ссылке **только в самом крайнем случае** — если JVM критически нуждается в памяти и находится на грани `OutOfMemoryError`.
    
    - _Зачем нужно:_ Идеально подходит для реализации кэшей в памяти (например, кэширование картинок). Если память есть — картинки лежат в кэше. Если память кончается — JVM сама очистит кэш, и программа не упадет.
        
3. **Weak Reference (Слабая ссылка):** GC удалит объект при **первой же сборке мусора**, если на него не осталось сильных или мягких ссылок.
    
    - _Зачем нужно:_ Часто используется для хранения метаданных (например, в структуре `WeakHashMap`), чтобы не мешать сборщику мусора очищать объекты (например, `ClassLoader`), когда они больше не используются в основной логике приложения.
        
4. **Phantom Reference (Фантомная ссылка):** Самый сложный тип. Из фантомной ссылки невозможно получить сам объект (метод `get()` всегда возвращает `null`). Она используется исключительно для того, чтобы получить уведомление (сигнал) о том, что объект был физически уничтожен сборщиком мусора.
    
    - _Зачем нужно:_ Используется как более надежная и гибкая альтернатива устаревшему методу `finalize()`, когда нужно выполнить сложную очистку внешних ресурсов после смерти объекта. Сборщик мусора удаляет объект из памяти только после нескольких циклов проверки фантомных ссылок.
