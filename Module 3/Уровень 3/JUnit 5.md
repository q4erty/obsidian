## 1. Тестирование в жизни программиста

Задача тестирования — доказать работоспособность кода. У тестов есть две главные цели:

1. **Позитивная проверка:** Убедиться, что программа делает то, что она _должна_ делать (при правильных входных данных выдает правильный результат).
    
2. **Негативная проверка:** Убедиться, что программа _не делает_ того, чего делать _не должна_ (при некорректных данных не ломается, а корректно выбрасывает ошибку).
    

Тестирование (особенно автоматизированное) помогает находить ошибки на ранних этапах и гарантирует, что при добавлении новых фич вы не сломаете старый функционал (регрессионное тестирование).

## 2. Жизненный цикл тестов и базовые аннотации

**JUnit 5 (Jupiter)** использует аннотации для управления процессом тестирования. Чтобы метод стал тестом, не нужно наследоваться от специальных классов, достаточно просто поставить правильную метку.

### Основные аннотации:

- **`@Test`**: Обозначает, что метод является тестовым. JUnit найдет все методы с этой аннотацией и запустит их.
    
- **`@BeforeEach`**: Метод с этой аннотацией будет запускаться **перед каждым** тестовым методом.
    
    - _Зачем нужно:_ Для подготовки "чистого" состояния перед каждым тестом (например, создание нового объекта или очистка списка), чтобы тесты не влияли друг на друга.
        
- **`@AfterEach`**: Метод запускается **после каждого** теста. Используется для очистки ресурсов.
    
- **`@BeforeAll`**: Запускается **один раз** перед выполнением всех тестов в классе. Метод _обязан быть статическим_. Используется для тяжелых операций (например, поднятие тестовой базы данных).
    
- **`@AfterAll`**: Запускается **один раз** в самом конце. Тоже статический.
    
- **`@Disabled`**: Отключает тест. JUnit пропустит этот метод при запуске (полезно, если тест временно сломан).

## 3. Методы проверок (Assertions)

**Assert** (Утверждение) — это сердце любого теста. Именно здесь мы сравниваем _ожидаемый_ результат с _фактическим_. Если утверждение ложно, тест падает.

### Базовые проверки (Дополнение для понимания):

- `assertEquals(expected, actual)`: Проверяет, равны ли два значения.
    
- `assertTrue(condition)`: Проверяет, что условие истинно.
    
- `assertFalse(condition)`: Проверяет, что условие ложно.
    
- `assertNull(actual)` / `assertNotNull(actual)`: Проверка на null.
    

### Продвинутые проверки (из презентации):

1. **`assertAll()`**:
    
    - _Проблема:_ В обычном тесте, если первый `assertEquals` падает, код дальше не выполняется, и мы не узнаем, прошли ли остальные проверки.
        
    - _Решение:_ `assertAll` принимает блок проверок и выполняет их **все**, даже если одна упала. В конце выдает отчет обо всех упавших проверках разом.
        
2. **`assertTimeout(Duration, Executable)`**:
    
    - Позволяет задать жесткий лимит времени на выполнение куска кода. Если код работает дольше — тест проваливается. Отлично подходит для проверки производительности алгоритма.
        
3. **`assertThrows(Exception.class, Executable)`**:
    
    - Используется для **негативного тестирования**. Мы ожидаем, что кусок кода выбросит конкретное исключение (например, при делении на ноль или передаче неверных аргументов). Если исключение вылетело — тест _пройден_. Если код отработал без ошибок — тест _упал_.

## 4. Параметризованные тесты

Часто нам нужно проверить один и тот же метод, но с разными наборами данных (например, валидацию email-адреса). Чтобы не писать 10 одинаковых методов, используют параметризацию.

_Вместо `@Test` используется аннотация **`@ParameterizedTest`**._

**Источники данных для параметризованных тестов:**

- `@ValueSource(ints = {1, 2, 3})`: Простой массив значений. Тест запустится 3 раза, передавая по очереди 1, 2 и 3 в качестве аргумента метода.
    
- `@EnumSource`: Передает значения из перечисления (Enum).
    
- `@MethodSource("имя_метода")`: Данные генерируются отдельным методом.
    
- `@CsvSource`: Позволяет передавать сразу несколько аргументов в виде строк (например, `@CsvSource({"apple, 1", "banana, 2"})`).

## 5. Организация и группировка тестов

Когда проект разрастается, тестов становится очень много. JUnit 5 предоставляет инструменты для их организации.

### Управление порядком (Order)

По негласному правилу тесты должны быть **независимыми** и их порядок не должен иметь значения. Но если это необходимо (например, интеграционные тесты):

- **`@TestMethodOrder(OrderAnnotation.class)`** — ставится над классом.
    
- **`@Order(1)`**, **`@Order(2)`** — ставится над конкретными методами для жесткого задания очередности запуска.
    

### Именование (DisplayName)

- **`@DisplayName("Мой красивый тест")`**: Позволяет задать человекочитаемое имя для теста, которое будет отображаться в логах и отчетах IDE вместо названия метода на английском (например, вместо `shouldReturnTrueWhenListIsEmpty()`).
    

### Тестовые наборы (Suites)

Специальные аннотации для объединения нескольких тестовых классов в одну группу, чтобы запускать их разом (например, "Все тесты базы данных" или "Все тесты безопасности").

- **`@Suite`**: Помечает класс как набор тестов.
    
- **`@SuiteDisplayName`**: Задает имя этой группе в логе.
    
- **`@SelectPackages("com.myproject.tests")`**: Указывает, что нужно запустить все тесты, лежащие в определенном пакете.
    
- **`@IncludeClassNamePatterns(".*Test")`**: Запускает только те классы, чьи имена подпадают под шаблон (например, заканчиваются на слово "Test").
