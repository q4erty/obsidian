## 1. Клиент-серверная архитектура

Весь современный веб построен на концепции **клиент-сервер**.

- **Клиент:** Программа (чаще всего браузер или ваше Java-приложение), которая инициирует соединение и отправляет **запрос** (Request).
    
- **Сервер:** Мощный компьютер или программа (например, Apache Tomcat), которая постоянно «слушает» сеть, принимает запросы, обрабатывает их и возвращает **ответ** (Response).
    

_Дополнение:_ Сервер никогда не начинает общение первым. Он только отвечает на запросы клиентов.

## 2. Устройство URL (Uniform Resource Locator)

**URL** — это унифицированный указатель ресурса (адрес в интернете).

Стандартная структура URL:

`протокол://хост:порт/путь?параметры#фрагмент`

- **Протокол:** Как общаться (например, `http` или `https`).
    
- **Хост:** Имя сервера или его IP-адрес (например, `google.com` или `192.168.1.1`).
    
- **Порт:** (Необязательно) Дверь на сервере. Для HTTP по умолчанию порт `80`, для HTTPS — `443`.
    
- **Путь (Path):** Конкретный файл или страница на сервере (например, `/images/logo.png`).
    
- **Параметры (Query String):** (Необязательно) Начинаются с `?`, разделяются `&`. Передают дополнительные данные (например, `?search=java&sort=asc`).
    
- **Фрагмент (Якорь):** Начинается с `#`. Указывает на конкретное место на веб-странице (обрабатывается только браузером).

## 3. Структура HTTP-сообщения

Протокол HTTP — это текстовый протокол. И запрос, и ответ имеют строгую, но простую структуру, состоящую из трех частей:

1. **Стартовая строка (Start Line):**
    
    - _В запросе:_ Метод + Путь + Версия протокола (например, `GET /index.html HTTP/1.1`).
        
    - _В ответе:_ Версия протокола + Статус код + Пояснение (например, `HTTP/1.1 200 OK`).
        
2. **Заголовки (Headers):** Набор пар `Ключ: Значение`, описывающих метаданные (кто отправляет, какой формат данных, размер и т.д.).
    
3. **Пустая строка:** Обязательный разделитель.
    
4. **Тело сообщения (Body):** Сами данные (HTML-код, картинка, JSON). Присутствует не всегда (например, в запросах GET тела обычно нет).
    

### Основные HTTP-методы:

- **GET**: Получить данные с сервера (безопасный метод, не меняет состояние).
    
- **POST**: Отправить новые данные на сервер (например, регистрация или оформление заказа).
    
- **PUT**: Обновить существующие данные целиком.
    
- **PATCH**: Частично обновить данные.
    
- **DELETE**: Удалить данные.

## 4. Коды HTTP-ответов (Status Codes)

Каждый ответ сервера содержит трехзначный код, который сходу говорит клиенту, как прошла операция.

Все коды делятся на 5 классов:

- **1xx (Информационные):** Процесс идет, подождите.
    
- **2xx (Успешные):** Все отлично. (Самый частый: `200 OK`, `201 Created`).
    
- **3xx (Перенаправления):** Ресурс перемещен. Клиенту нужно сходить по другому адресу (`301 Moved Permanently`, `302 Found`).
    
- **4xx (Ошибки клиента):** Вы сделали что-то не так (вы — клиент).
    
    - `400 Bad Request` — кривой синтаксис запроса.
        
    - `401 Unauthorized` — вы не авторизованы (нет логина/пароля).
        
    - `403 Forbidden` — авторизованы, но нет прав доступа.
        
    - `404 Not Found` — такого адреса не существует.
        
- **5xx (Ошибки сервера):** Вы все сделали правильно, но сервер сломался.
    
    - `500 Internal Server Error` — неожиданная ошибка в коде сервера.
        
    - `502 Bad Gateway` / `503 Service Unavailable` — сервер перегружен или выключен.

## 5. REST Архитектура (Representational State Transfer)

В презентации упоминается концепция REST — это набор правил (стиль архитектуры) для построения удобных веб-сервисов (API).

**Главные принципы REST:**

1. **Client-Server:** Строгое разделение клиента (UI) и сервера (хранение данных).
    
2. **Stateless (Без состояния):** Сервер не запоминает предыдущие запросы клиента. Каждый запрос должен содержать **всю** информацию (например, токен авторизации), необходимую для его выполнения.
    
3. **Единообразие интерфейса (Uniform Interface):** Стандартизированные пути доступа к ресурсам (например, `GET /users`, `POST /users`, `DELETE /users/5`).

## 6. Эволюция HTTP: Версии протоколов

- **HTTP/1.1:** Классический текстовый протокол.
    
- **HTTPS:** Тот же HTTP, но обернутый в криптографический протокол (SSL/TLS) для защиты от прослушивания (шифрование).
    
- **HTTP/2 (Инициатива Google):**
    
    - Стал бинарным (передача байтов, а не текста — это быстрее).
        
    - Обязательное шифрование.
        
    - Мультиплексирование: несколько запросов передаются параллельно по одному TCP-соединению (не нужно ждать очереди).
        
    - Сжатие заголовков (HPACK).
        
    - Server Push: сервер может прислать стили и скрипты еще до того, как браузер их попросит.
        
- **HTTP/3:** Отказ от тяжелого протокола TCP в пользу легкого UDP (с надстройкой QUIC). Это решает проблему блокировки начала очереди и делает интернет еще быстрее, особенно на нестабильных мобильных сетях.

## 7. Работа с HttpClient (Java 11+)

До Java 11 в стандартной библиотеке был старый, неудобный и синхронный класс `HttpURLConnection`. Разработчикам приходилось использовать сторонние библиотеки (например, Apache HttpClient или OkHttp).

В Java 11 появился новый, современный **`java.net.http.HttpClient`**.

### Основные компоненты:

1. **`HttpClient`**: Сам клиент (браузер в мире Java). Настраивается один раз (таймауты, прокси, версия HTTP).
    
2. **`HttpRequest`**: Описание вашего запроса (куда стучаться, каким методом, какие заголовки передать). Создается через паттерн Builder.
    
3. **`HttpResponse`**: То, что мы получаем от сервера (статус код, заголовки, тело ответа).
    

### Пример выполнения запроса:

Java

```
// 1. Создаем клиента
HttpClient client = HttpClient.newHttpClient();

// 2. Формируем запрос
HttpRequest request = HttpRequest.newBuilder()
        .uri(URI.create("https://api.github.com/users/defunkt"))
        .GET() // По умолчанию и так GET, но можно указать явно
        .header("Accept", "application/json") // Просим вернуть JSON
        .build();

// 3. Отправляем запрос и получаем ответ
// BodyHandlers.ofString() говорит клиенту: "Прочитай тело ответа и преврати его в String"
HttpResponse<String> response = client.send(request, HttpResponse.BodyHandlers.ofString());

// 4. Анализируем результат
System.out.println("Статус: " + response.statusCode());
System.out.println("Тело: " + response.body());
```

### Синхронность и Асинхронность

- `client.send(...)` — блокирующий (синхронный) метод. Поток остановится и будет ждать ответа от сервера.
    
- `client.sendAsync(...)` — асинхронный метод. Возвращает `CompletableFuture`. Поток не блокируется, а код выполнится (через callback), когда ответ придет.

## 8. Работа с Cookie (Куки)

Поскольку HTTP — это протокол без состояния (stateless), сервер не помнит вас между запросами. Чтобы реализовать авторизацию или "корзину товаров", придумали **Cookie**.

- **Как это работает:** При успешном логине сервер присылает заголовок `Set-Cookie: session_id=123`.
    
- Браузер (или HttpClient) сохраняет эту "печеньку".
    
- При каждом следующем запросе к этому же серверу клиент автоматически прикрепляет заголовок `Cookie: session_id=123`. Сервер видит её и понимает: "А, это тот самый авторизованный пользователь".
    

В Java новом `HttpClient` есть встроенный `CookieHandler` (или `CookieManager`), который может автоматически запоминать и подставлять куки, чтобы вам не приходилось парсить заголовки вручную.
